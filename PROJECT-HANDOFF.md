## Deploy pipeline (`.github/workflows/deploy.yml`)

1. Checkout (full history, `fetch-depth: 0` — needed for delta sync's `git diff`).
2. `npm ci`, then `npx gulp _build` (compiles all SCSS → `assets/css/*.min.css` and bundles JS → `assets/js/*.min.js`).
3. `milanmk/actions-file-deployer@1.18` deploys over SFTP straight from the repo root, using **delta sync**: it diffs `git diff <previous commit>..<head>` and only uploads/deletes what changed, instead of re-uploading the whole theme every run. `workflow_dispatch` can override to `sync: full` for a complete re-upload — this exists specifically to recover when delta sync drifts (see "Known issue" below, you may need this).
4. `sync-delta-includes` in the workflow force-includes the compiled CSS/JS bundles on every deploy regardless of what git diff reports, because the build step regenerates them in the runner's working directory without re-committing — a commit that only touches `source/scss/*.scss` would otherwise look like "no CSS changed" to a naive git diff.

### CRITICAL: commit-message hazard

`milanmk/actions-file-deployer`'s own `action.yml` unconditionally embeds `${{ github.event.head_commit.message }}` into a **double-quoted string inside its generated bash script** (used to build a webhook payload the workflow doesn't even use). If a commit message contains a literal `"` character, it breaks out of that quoted string, and *whatever shell-meaningful character shows up later in the message* — `<`, `>`, `(`, `)`, etc. — gets parsed as real bash syntax, and the whole step fails at parse time with an "unexpected token" error. This happened twice in this project (once with `<`, once with `(`).

**Rule: never use a literal double-quote character in a commit message that reaches `dev` or `main`.** That alone prevents the breakout regardless of what follows it — once there's no quote to break out of, no follow-on character can misparse either. As extra margin, also avoid backticks and angle brackets. Write commit messages in plain prose without quoted snippets. This is documented in the comment above the deploy step in **both** `deploy.yml` and `deploy-production.yml` (kept in sync — if you ever update one, update the other) — read it before writing a commit message if unsure.

**This applies to merge commit messages too**, not just ordinary commits — including the merge that lands a `dev`-to-`main` PR. A default, unedited "Merge pull request #N from .../dev" message is safe. A manually-edited one that quotes a filename or code snippet is not. When merging `dev` into `main` on GitHub, don't touch the default merge commit message.

If you ever need to fix a bad commit message that already broke a run: `git commit --amend -F -` with a clean message, then the human operator needs to `git push --force-with-lease` (not a plain push) since history was rewritten. **Watch out**: doing this can itself break delta sync (see below).

### KNOWN ISSUE — delta-sync drift after a force-push (RESOLVED, but can recur)

A force-push (amending a commit to fix its message) can trigger this failure mode: delta sync tries to diff against the previous commit SHA it remembers, but that SHA no longer exists after the history rewrite. The action logs an annotation: `Invalid base commit for delta synchronization: <sha>. Please ignore if this is an initial commit or newly created branch.` — and despite the run showing green/"succeeded," it silently uploads **nothing**, because it couldn't compute a diff. This happened once in this project; the fix was live on `dev`/GitHub but not on staging until resolved.

**Recovery:** trigger the deploy workflow manually via `workflow_dispatch` with `sync: full` (GitHub → Actions → "Build & Deploy (SFTP)" → "Run workflow" → set "File synchronization" to `full` → Run). This forces a complete re-upload regardless of git history. This was done and confirmed the drift was resolved (see "dev → main merge and production deploy" section below for the verification technique). **This risk only applies after a force-push** (history rewrite) — an ordinary merge or fast-forward push preserves ancestry and delta sync works normally, no need to pre-emptively run `sync: full` for routine pushes.

## Established workflow conventions

Every code change in this project followed this pipeline before committing:

1. Edit files with the Edit/Write tools (not ad-hoc shell text manipulation).
2. **Verify PHP syntax** via an AST-based checker: `node /tmp/phpcheck/check.cjs <file>` (a `php-parser`-based Node script set up earlier in the project — if it's missing in a fresh sandbox, note the checker itself is external to the repo, not committed).
3. **Check for CRLF line endings** in changed files: `grep -c $'\r' <file>` should be `0` for PHP files edited directly (the repo has `.gitattributes` with `* text=auto eol=lf` to normalize this on commit, but it's still worth checking your own edits didn't introduce CRLF).
4. `git diff` review before committing — read the actual diff, don't assume the edit tool did what you intended.
5. `git add <specific files>` (never blanket `git add -A` — several stray old files exist in the repo root that should never be re-added) then `git commit -F -` with a heredoc, using a plain-prose message (see commit-message hazard above).
6. For SCSS changes: rebuild with `npx gulp build:styles` (or `npx gulp _build` for a full build including JS/fonts/icons) and commit the regenerated `assets/css/*.min.css` files alongside the source `.scss` change — the compiled output is what's actually deployed.

## Filter-listing first-paint server-rendering (deep dive — most recent work)

### The problem this solved

The site has several "filter and browse posts" templates (sector, persona, topic, search, whats-new, post-filters, filter-types, favourites). Originally, on first page load these templates rendered an **empty** posts grid and empty filter-pills area, then JavaScript (`main.js`) fired an AJAX call on `DOMContentLoaded` to fetch and inject the actual content. This caused a real, user-reported bug: **first-load content could differ from what re-selecting the same filters via AJAX would show**, because the two code paths (PHP-first-load-that-doesn't-actually-render vs. the AJAX handler) could drift out of sync, plus there was a visible flash/delay on every page load.

### The fix pattern (applied to 7 templates)

For each filter-listing template:

1. **Buffer the render early**: before the filter-dropdown-building code runs, call `ob_start(); adapt_render_filter_posts(); $posts_container_html = ob_get_clean(); wp_reset_postdata();` and read `$adapt_visible_terms = $GLOBALS['adapt_visible_terms'] ?? [];`. Also init `$active_filter_pills = [];`.
2. **In each filter dropdown's term loop**, compute `$is_visible = in_array($term->slug, $adapt_visible_terms['<taxonomy-key>'] ?? [], true);` and append `style="display:none;"` to the button when not visible (this is the "dim empty filter buttons" behavior — buttons for terms with zero matching results are hidden on first paint, matching what AJAX filtering would do). When a term is the active one (matches the current `$_GET` value), also push it into `$active_filter_pills[]`.
3. **Build the pills HTML** right before the Results section: concatenate `<button type="button" class="filter-pill" data-filter="...">...` for each collected pill, and emit `<script>window.adaptFilterUIServerRendered = true;</script>`.
4. **Replace the empty pills div** (`<div class="active-filter-pills" style="display:none;"></div>`) with the populated one, and replace `<?php adapt_render_filter_posts(); ?>` with `<?= $posts_container_html; ?>`.

Taxonomy key mapping used in step 2: `topic`→`topic`, `type`→`filter-types`, `sector`→`sector-analysis`, `persona`→`persona-mapping`, `trending-themes`→`trending-themes`, `event`→`insights-event`, `date`→`date`.

`main.js`'s INITIAL LOAD block checks `window.adaptFilterUIServerRendered === true` and skips `buildActiveFilterPills()`/`hideEmptyFilters()` on first paint when set (both still run normally on every subsequent AJAX filter interaction — only the *first paint* is skipped). Pill clicks are handled by one delegated handler on `.active-filter-pills` reading `data-filter` off whichever pill was clicked, so it works for both server-rendered and JS-rendered pills uniformly.

### Undefined-variable GET-mismatch bug class (recurring, worth knowing about)

Found and fixed in three separate templates: a template parses `$_GET['theme']` (or `$_GET['sector']`) into a variable like `$events` (or `$sectors`) near the top of the file, but a dropdown-building block *elsewhere in the same file* checks a **different, never-defined** variable name (`$themes`, `$sector`) for its active-state logic. PHP's `empty()`/`===` on an undefined variable is falsy but doesn't fatal or warn loudly, so this silently breaks "highlight the right filter button for a bookmarked/shared URL" without ever throwing a visible error. If you're auditing any of these templates further, grep for every `$_GET[...]` parse at the top of the file and cross-check every variable name used in dropdown loops below it — don't assume matching names are correct.

### Follow-up CSS bug found and fixed after the above

After the persona-filters template started correctly setting `style="display:none;"` on `#featured-post-persona` when there's genuinely no featured post to show, it turned out `_post-new.scss` had a pre-existing rule:

```scss
body.template-persona-filters.filter-active-1.persona-active {
    section.featured-persona-post {
        display: block!important;
    }
}
```

Since both this rule and the inline style are as strong as `!important` gets in different cascade tiers, the `!important` stylesheet rule always won over the plain inline style — meaning the section could be forced visible as an **empty box** even when there was nothing to show. Fixed by adding a `:not([style*="display:none"])` guard to both this rule and its `template-sector-filters`/`sector-active` counterpart, so the forced-visible CSS only applies when the element doesn't already carry the PHP-driven "nothing to show" signal. Source: `source/scss/templates/_post-new.scss` (search for `filter-active-1.persona-active`). Compiled into `core.min.css` and the four `tpl-*.min.css` bundles that also pull in `_post-new.scss`. **This is the fix currently stuck behind the delta-sync issue described above — verify it's actually live before considering this done.**

This module's `.active-filter-pills` div is still hardcoded empty (`style="display:none;"`) — it was **not** wired up to show server-rendered pills the way the filter-listing templates below were, since that would need a small `main.js` change to make server-rendered pills clickable/removable in the `.speaker-module` system specifically. ## Sitewide multi-second TTFB investigation and fix

A report of slow TTFB on filter/archive pages led to a much bigger finding than initially scoped. Documenting the full arc here, including a methodology mistake, because the corrected approach (server-side profiling via Query Monitor) is the right way to pick this class of problem up again in the future.

**First attempt (commit `c50b0d1`) — turned out to be a red herring, not reverted, still harmless.** `adapt_get_visible_terms()` (shared by `ajax_load_filtered_posts()` and `adapt_render_filter_posts()`) was suspected as the cause of multi-second TTFB on filter pages, based on a "3 second → 170ms" browser-timing comparison. That comparison was invalid: the "before" measurement had a cache-busting query string, the "after" measurement didn't, and WP Rocket's full-page cache — which only ever applies to a clean-URL, logged-out, non-AJAX request — was silently serving the "after" load from cache instead of actually re-running the fixed code. Rigorous re-testing (repeated identical AJAX calls, which bypass WP Rocket regardless of query string) showed the caching fix added in `c50b0d1` made no measurable difference, and the exact same multi-second delay showed up on every page type, including ones that never call this function at all (homepage, single-post articles). The caching fix itself is still correct and harmless (keyed on args/taxonomies/membership type, 5-minute TTL, invalidated on `save_post`/`created_term`/`edited_term`/`delete_term`) but it was not the actual cause of the reported slowness.

**Lesson for next time**: browser-side Resource Timing / Network tab comparisons on this site are unreliable unless you either (a) hit an AJAX endpoint directly (bypasses WP Rocket's page cache entirely), or (b) add a cache-busting query string to **both** the before and after measurement consistently (WP Rocket's default config excludes any URL with a query string from its page cache). A clean-URL "after" reading that looks dramatically faster than a query-string "before" reading is probably a cache hit, not a real fix.

**Real diagnosis — Query Monitor.** At this point browser-side timing tools couldn't say anything more, since the delay was sitewide and DB/server-side. The user installed the Query Monitor plugin on staging at request. QM's toolbar UI needs the WP admin bar visible (front-end toolbar visibility depends on the logged-in user's own profile setting and `manage_options` capability — access it via `/wp-admin/` directly if the front-end toolbar is hidden), but its **raw profiling data is embedded in every page's HTML regardless of toolbar visibility**, as an inline `<script id="query-monitor-inline-data">` tag. Access it from any page (including via a headless fetch of the HTML) with:

```js
const qm = window.QueryMonitorData;
qm.data.overview.data.time_taken;        // total PHP generation time, seconds
qm.data.db_queries.data.rows;            // array of {sql, ltime, trace: {component, frames}, result}
qm.data.php_errors.data;                 // PHP warnings/notices/deprecated messages
```

`trace.frames` is an array of `[fileIndex, lineNumber]` pairs; resolve `fileIndex` against the top-level `qm.frames` object to get the actual file path and calling function for each query — this is how the root cause below was found (walked the frames of every slow query until a theme file showed up).

**Root cause found**: on the homepage, QM showed 4.9–6.8 seconds total generation time, of which 2.08+ seconds (up to ~40–50%) was 37 calls to WordPress core's `attachment_url_to_postid()` — a function that runs an uncached, unindexed query against `wp_postmeta.meta_value` every single time it's called. A cached wrapper for this exact function, `adapt_attachment_url_to_postid()`, already existed in `functions.php` from earlier work in this project, but had only ever been wired into one file (`templates/components/_event-card.php`). Every other article card, event card, header, footer, and featured/resources block across the theme (56 other files, 178 call sites) was still calling the raw uncached core function directly.

**Fix (commit `7e13bdf`)**: mechanical substitution of all 178 remaining raw `attachment_url_to_postid(` calls with the existing `adapt_attachment_url_to_postid(` wrapper, across 55 files (one file already used the wrapper correctly and was left untouched). No other logic changed. Verified via AST parse check on every touched file, plus grep checks confirming no call site was double-wrapped and the wrapper's own internal call to the real core function (inside its own definition) was left untouched, so it doesn't recurse into itself.

**Verified live on staging after deploy**: first load after deploy still paid the query cost once per URL (transient cache was cold), but every subsequent load showed the attachment-lookup queries gone completely — total DB query time dropped from 2.08s to ~0.10s, total page generation time dropped from 4.9–6.8s to a consistent ~1.65–1.67s, and total query count dropped from 231–312 down to ~192.

**If picking this up further**: QM's `qm.data.php_errors.data` showed ~151 PHP warnings/notices/deprecated-function-usage messages on the homepage at the time of this investigation, and a `doing_it_wrong` panel showed 1 warning. The theme-owned ones were triaged and fixed (see next section) — what's left after that is out of theme scope.

## Homepage LCP regression traced to a plugin's blocking HTTP call, not the slider (commit `3bfcd0b`)

User reported an LCP regression on the homepage, attributing it to the hero slider. Investigation used `PerformanceObserver({type: 'largest-contentful-paint', buffered: true})`, Resource Timing, and Navigation Timing to check the slider markup first, since that was the reported suspect — and ruled it out. The `.resources-featured-slider`'s `<img>` already had correct `fetchpriority="high" loading="eager" decoding="async"`, and `source/scss/global/_base.scss:60`'s FOUC-prevention rule (`.resources-featured-slider:not(.slick-initialized) .resources-featured-slide:not(:first-child) { display: none; }`) correctly scopes to non-first slides only, so it wasn't hiding the LCP candidate either.

**Real cause, found via a Query Monitor panel not used in earlier passes**: `qm.data.http.data.http` (outbound HTTP requests made during the request) showed a synchronous, blocking ~1.2 second `GET` to `https://app.customgpt.ai/api/v1/projects/{id}/settings` on every single homepage load. Grepped the theme for any PHP-side reference to `customgpt` — zero hits; the theme's own CustomGPT integration is entirely client-side JS, already deferred until the chat widget is opened (see `footer.php`'s `ensureCustomGptInit()`). The call is made by the `customgpt-chat-widget` plugin's own PHP bootstrap, unconditionally, on every page load — this single call accounted for the majority of the page's non-database PHP execution time and was delaying LCP paint indirectly (by delaying TTFB / first-byte, not by blocking the image itself).

**Fix**: added `adapt_is_customgpt_settings_request()` plus a `pre_http_request` filter and an `http_api_debug` action pair in `functions.php`, caching the plugin's settings response via a transient (`adapt_cgpt_settings_<md5(url)>`, 15-minute TTL) — short-circuits the request on cache hit, populates the cache from the one real request that does go through. Deliberately caches only the plain-data fields (`headers`, `body`, `response`, `cookies`) rather than the raw response array, dropping `http_response` (a `WP_HTTP_Requests_Response` object) since it isn't guaranteed to survive a transient's serialize/unserialize round trip. This is a WordPress-hook-based fix in theme code only — no plugin files touched, so it survives the plugin's own updates.

**Verified live on staging after push**: `qm.data.http.data.http` on a fresh homepage load now shows zero customgpt.ai calls (was one, ~1.2s) and total PHP generation time dropped to ~1.5s. However, the user then reported the LCP delay was still visible — "took some few seconds before the slick transforms" — pointing back at the slider itself rather than the HTTP call. This led to a second, distinct fix (next section).

## Homepage LCP, second cause: resources-featured-slider's slick() init queued behind ~16 unrelated carousels (commit `87e345c`)

After the customgpt fix above, re-ran the `PerformanceObserver({type: 'largest-contentful-paint', buffered: true})` live trace on the homepage and found the browser logging **two** LCP candidates for the same slider image: an initial paint around 1828ms, then a second, larger-area candidate at 2380ms (browsers/Lighthouse report the *last* LCP candidate as the metric, so the real LCP value was the later one, not the first paint). The ~550ms gap between them lined up with `domContentLoadedEventEnd` (~2117ms) plus a delay — i.e., with when slick.js actually got around to transforming this slide's layout, matching the user's own description of the delay.

Root cause: `.resources-featured-slider`'s `.slick({...})` call in `source/js/main.js`'s `$(document).ready()` handler was the 17th of ~17 sequential `.slick()`/`.owlCarousel()` init calls (`.kit-slider-container`, `.featuredSlider.portal`, `.data-article-slider`, `.eventSlider`, `.center`, `.preview-main-slider`, `.preview-thumbnail-slider`, `.data-insights-related`, `.quote-slider-module`, `.sliderBlockCarousel`, `.fullPageSliderCarousel`, `.speaker-gallery`, `.quote`, `.articlesCarousel`, `.articlesCarouselTaxonomies`, then finally `.resources-featured-slider`). Most of these selectors don't match anything on the homepage — but even a non-matching jQuery selector still costs a full DOM query, and all of them run synchronously, in order, before slick ever reaches the one carousel whose first slide is this page's (and several other templates') LCP image.

**Fix**: moved the `.resources-featured-slider` `.slick({...})` block to run first in the ready handler — immediately after the two delegated accessibility event bindings (`'init'`/`'beforeChange'` on `.slick-slider`, which use event delegation via `$(document).on(...)` so they still catch this slider's init regardless of where it's called from, as long as they're bound first) — ahead of every other carousel. Pure reordering: no config, timing, or other carousel's behavior changed. Rebuilt `assets/js/main.min.js` via `npx gulp build:scripts` and confirmed in the compiled output that `resources-featured-slider` now appears before `kit-slider-container` (previously last, now first).

**Verified live on staging after push, but the LCP delay was still present** — reordering alone didn't help, and the user confirmed the delay was still visible. Live re-tracing found the actual, deeper cause (next section).

## Homepage LCP, third cause: whole document.ready() handler blocks the paint (commit `fa596db`)

Re-ran the LCP `PerformanceObserver` trace on the homepage after the reorder fix landed and found the same two-candidate pattern as before, with almost the same timing gap (~630ms this time vs ~550ms before) — the reorder hadn't actually changed anything measurable. Added a `PerformanceObserver({type: 'longtask', buffered: true})` trace and found a ~240ms synchronous JS task starting right after `domContentLoadedEventEnd`, ending right before the browser's second (final) LCP paint for the slider image. This explained why the reorder fix didn't help: JS blocks rendering, so the browser can't paint the result of the (now-first) `.resources-featured-slider` `.slick()` call until the *entire* `document.ready()` handler finishes executing — no matter how early within that handler the call runs.

Identified `matchHeightInit()` (called right after the STANDARD/`_maps.js` include, immediately following the slider's slick init) as the almost-certain dominant cost inside that task: it calls jQuery's `matchHeight()` plugin — which forces a synchronous layout read — across roughly 32 separate selector groups sitewide (cards, kits, partners, footer columns, blog grids in 7+ layout variants, agenda blocks, mega menu, etc.), none of which are above-the-fold LCP content on the homepage.

**Flagged to the user before implementing**, since this fix touches `main.js`'s shared, sitewide `document.ready()` handler (loaded on every template, not just the homepage) — a wider blast radius than the rest of this session's changes. User approved.

**Fix**: wrapped `resize(); matchHeightInit(); if (typeof select2 === 'function') select2(); outsideContainer(); scrollMobile();` in a single `requestAnimationFrame(function () {...})` call, so the browser gets a chance to paint before this layout-thrashing setup work runs. Confirmed safe by checking that `ww`/`wh` (the two outer-scope variables `outsideContainer()`/`scrollMobile()`/`resize()` set) are only ever read from inside other event-bound functions (`headerSet()`, the window resize handler) elsewhere in the file, never synchronously inline within the same `ready()` callback — so deferring their initial assignment by one animation frame doesn't create a race with anything else in that same handler. The other three call sites of these same functions (window resize handler, AJAX filter-load success callback) were left untouched since they already run after initial page load. Rebuilt `assets/js/main.min.js` via `npx gulp build:scripts` and confirmed the `requestAnimationFrame` wrapper in the compiled output.

**Verified live on staging after push — the rAF wrapper made no measurable difference.** Re-ran the same LCP/Long Task trace: still a ~540–590ms gap between the slider's two LCP candidates, and the Long Task (now ~179ms, starting just after `DOMContentLoaded` instead of before it) still landed right before the second, final LCP paint. The deferral moved *when* the heavy block started, not whether it still blocked the same paint.

**Root cause of the rAF miss**: `requestAnimationFrame()` callbacks run as part of the *current* frame's rendering steps, before that frame paints — not after. Wrapping heavy synchronous work in rAF only delays its start by a few milliseconds; it doesn't insert an actual paint in between. What's needed is a real macrotask boundary, which is what `setTimeout(fn, 0)` provides — the browser's rendering pipeline (style/layout/paint) gets a chance to run between the end of the current task and the start of the timer callback.

**Fix (commit `91a1b67`)**: swapped `requestAnimationFrame(function () {...})` for `setTimeout(function () {...}, 0)` around the same `resize()`/`matchHeightInit()`/`select2()`/`outsideContainer()`/`scrollMobile()` block — no other logic changed. Rebuilt `assets/js/main.min.js` and confirmed `setTimeout(...,0)` in the compiled output in place of `requestAnimationFrame`.

**Verified live on staging after push — still no change.** The `setTimeout(0)` deferral also made no measurable difference: the long task still landed right before the second, final LCP paint, just shifted a bit later in absolute time. Three different JS-timing interventions in `main.js` (reorder, rAF, setTimeout) had now all failed to move this specific metric, which was the signal to stop iterating on JS scheduling and look for a cause outside `main.js` entirely.

## Homepage LCP, actual root cause: customgpt widget's CSS leaking `font-family: Inter` sitewide (commit `12ae9dd`)

Correlated the live Resource Timing data against the LCP trace directly rather than continuing to guess at JS timing. Found a Google-hosted "Inter" web font (`fonts.gstatic.com/s/inter/...woff2`) finishing its download at a timestamp that landed consistently between the slider's first and second LCP paints, across every test run. Confirmed via `document.fonts` and `getComputedStyle(document.documentElement).fontFamily`, which reported `"Inter, -apple-system, BlinkMacSystemFont, sans-serif"` instead of the theme's own font stack.

Traced this to `wp-content/plugins/customgpt-chat-widget/dist/widget/customgpt-widget.b16.min.css`, which contains an unscoped `body, html { font-family: Inter, -apple-system, BlinkMacSystemFont, sans-serif; }` rule — no containing class or ID limiting it to the widget's own UI, so it applies to the entire document. It loads after the theme's own CSS with identical specificity (plain element selectors on both sides), so it silently wins the tie and overrides the theme's `html`/`body` `font-family` sitewide, confirmed via live `getComputedStyle`.

The theme's own `$font-base` (`'Helvetica Neue', 'Helvetica', 'Arial', sans-serif` — a plain system stack, nothing to download) was correctly declared on `html`/`body` in `_base.scss` all along; it was just losing the specificity tie to the widget's leaked rule. Because of that, every page load had to wait for Inter to download from Google before any text relying on the inherited `font-family` rendered in its final font. Once that download completed mid-page-load, the resulting reflow resized the `resources-featured-slider`'s column via its `padding-top`-based aspect-ratio trick (see the `.image-container { padding-top: 56.25%; }` rule in `_post-new.scss`) — well after first paint, and completely independent of anything in `main.js`, which explains why none of the three JS-timing fixes touched it.

**Fix**: added `!important` to both existing `font-family: $font-base;` declarations for `html`/`body` in `source/scss/global/_base.scss`, restoring the system font stack regardless of the plugin CSS's load order. This project already uses `!important` for the identical "defend against third-party plugin CSS" reason in `_forms.scss`, so this matches existing convention rather than introducing a new pattern. Rebuilt `assets/css/global.min.css` (the only compiled bundle that includes `_base.scss` — confirmed via `main-global.scss`/`main.scss`'s import chains, and confirmed `global.min.css` is enqueued on every single page via `adapt_enqueue_template_styles()` in `functions.php`) and confirmed `!important` in the compiled output. Stylelint clean on the changed file.

**Verified live on staging after push**: `getComputedStyle(document.documentElement).fontFamily` correctly reports the system stack again, confirming the fix landed and wins the specificity tie as intended. **However, the LCP size jump (78495→91937 px²) was still identical and unchanged** — the font-family fix was real and worth keeping, but it wasn't (solely) responsible for this specific symptom. That was the signal to instrument the actual resize event directly instead of continuing to reason from correlation.

## Homepage LCP/CLS, actual final cause: customgpt widget's embedded chat box pushes the whole page down as it hydrates (commit `559f447`)

Combined `navigate` + an immediate polling script (via `browser_batch`, to minimize the round-trip gap that had been causing earlier polling attempts to start after the page had already settled) to catch the resize event directly with `getBoundingClientRect()`. Found the featured slider's image sits partially below the fold at this viewport size — the LCP "size" metric is the *visible, viewport-intersecting* area of the element, not its full box — so a change in how much of the image intersects the viewport (without the image's own CSS box changing at all) would also explain the two different "size" readings.

Walking up the DOM from `.resources-featured-slider` to `<body>` found the actual cause: `#customgpt-chat-1` (`class="customgpt-chat-embed customgpt-embedded-widget"`), the CustomGPT plugin's "ADAPT Intelligence" embedded search/chat box, sits in **normal document flow** directly above `<main>` (`position: static`, confirmed via `getComputedStyle`) — not `position: fixed` like a typical chat-launcher widget. Its container starts empty in the raw server HTML (rendered via `[customgpt_chat mode="embedded"]` in `templates/template-portal-flexible.php`, gated behind an `agent_tester` user-role check — confirmed this only renders for that role, not anonymous visitors, via a body-class/cookie/`/wp-admin/` check) and only reaches its full height once its own React/Tailwind bundle hydrates client-side (`innerHTML` shows a `"widget-mode embedded-mode"` wrapper, confirming a client-rendered app, not server-rendered markup). While it grows from 0 to its real height, everything below it on the page — including the featured slider — gets pushed down in real time, which is exactly what was changing the slider's viewport-intersecting area and showing up as the delayed second LCP paint. A screenshot confirmed this is a legitimate, prominent, intentionally-shown homepage feature (branded "ADAPT Intelligence — BETA" with suggested prompts), not something to hide — the fix needed is a standard CLS-prevention space reservation, not any change to the widget's content or visibility.

**Fix**: added a `min-height` to the existing `body.template-portal-flexible .customgpt-chat-embed` rule in `source/scss/partials/_customgpt.scss` (a dedicated CustomGPT-widget partial already existed, alongside the widget's existing `padding-top: 111px` rule). Sized from live `getBoundingClientRect()` measurements at three viewport widths — ~517px at ~530px wide, ~547px at 1440px, ~583px at 375px (mobile) — using each bucket's highest observed value plus a small safety margin, via `@include responsive(767)` for the mobile breakpoint. Rebuilt `assets/css/global.min.css` (compiled via the `partials/**/*.scss` glob import in `main-global.scss`) and confirmed both rules in the compiled output. Stylelint clean.

**Verified live on staging after push**: LCP size-jump gap shrank from a ~17% jump (78495→91937 px²) down to ~2% (46172→47045 px²) — a large, clearly successful improvement. However, the desktop `min-height: 610px` value used on mobile at the time left a large, visibly awkward empty gap between the widget's suggested prompts and the slider below on mobile widths (screenshot-confirmed) — worse cosmetically than the small layout shift it was preventing.

**Follow-up per explicit user request** (commit `aaf909a`): user clarified the performance concern this whole thread addresses is desktop-only, and asked to remove the mobile gap, deferring mobile CLS to a later pass. Restructured the rule from an unconditional base `min-height` overridden on mobile, to a single `@media (min-width: $break-mobile)` (768px, the exact complement of this file's `@include responsive(767)` breakpoint) wrapping the desktop `570px` value — mobile now gets no forced `min-height` at all, natural sizing. Verified both breakpoints live *before* committing by injecting a temporary override `<style>` tag into the currently-deployed page (previewing the fix without needing to deploy first): at 375px width the widget settles at its natural ~583px with the slider sitting directly beneath it, no gap (screenshot-confirmed); at 1440px width `getComputedStyle` confirmed `min-height: 570px` still applies unchanged. Rebuilt `global.min.css`, confirmed the compiled media query, stylelint clean.

**Mobile CLS/performance is a known, explicitly-deferred follow-up** — not addressed further per the user's own request, revisit if/when mobile becomes a priority.
