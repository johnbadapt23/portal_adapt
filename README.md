# Portal ADAPT — WordPress Theme

WordPress theme for the research/membership portal (MemberPress-gated content, partner/sector/topic templates). Built on a Gulp + npm asset pipeline; ships to the staging server via GitHub Actions over SFTP.

## Requirements

- Node **22** (see `.nvmrc` — run `nvm use` if you use nvm)
- npm 10+
- A local WordPress install if you want to run the live-reload dev server (`gulp __start` proxies `http://adapt.local`, configurable in `source/gulp/config.js`)

## Quick start

```bash
npm install          # installs everything in package.json into node_modules
npx gulp _build       # one-off production build → writes into assets/
```

That's it for a one-time build. `assets/css/main.min.css` and `assets/js/main.min.js` get regenerated from `source/scss` and `source/js`; everything else `_build` touches (fonts, icons, images) is also written into `assets/`.

For active local development with live reload:

```bash
npx gulp __start
```

This proxies your local WordPress install (edit `source/gulp/config.js` → `serve.url` if your local domain isn't `adapt.local`) and rebuilds automatically on file changes.

## Build commands

| Command | What it does |
|---|---|
| `npx gulp _build` | Full production build: fonts, icons, images, scripts, styles, then a PHP reload pass |
| `npx gulp __start` | Starts BrowserSync proxy + file watcher for local dev |
| `npx gulp watch` | Just the file watcher (used internally by `__start`) |
| `npx gulp build:styles` | Compile `source/scss` + vendor CSS → `assets/css/{global,core,tpl-agenda,tpl-events,tpl-flexible,tpl-home,tpl-portal-flexible}.min.css` (see "CSS bundle split" below) |
| `npx gulp build:scripts` | Bundle `source/js` + vendor JS → `assets/js/main.min.js` |
| `npx gulp build:images` | Optimize `source/images/**` → `assets/images/` |
| `npx gulp build:fonts` | Generate webfonts from `source/fonts/*.{ttf,otf}` (currently no source fonts checked in — this is a no-op unless you add some) |
| `npx gulp build:icons` | Generate the icon font from `source/icons/*.svg` → `assets/fonts/icons.*` + `source/scss/global/_icons.scss` |
| `npx gulp build:favicons` | Regenerate the favicon set via realfavicongenerator.net (needs network access) |
| `npx gulp deploy:zip` / `deploy:ftp` / `deploy:git` | Legacy one-off deploy tasks — not used by CI, kept for manual/local use |

The build pipeline is Gulp 5. Frontend libraries (Slick, Owl Carousel, Magnific Popup, Select2, FlexSlider, MediaElement, isotope-layout, perfect-scrollbar, etc.) are plain npm dependencies — `source/gulp/paths.js` lists exactly which files get pulled from `node_modules` into the bundle.

## Project structure

```
functions.php, header.php, footer.php, index.php, style.css   → active theme entry points
includes/, templates/, memberpress/, download-monitor/         → PHP templates & partials
source/                                                         → build INPUT (scss, js, images, icons, gulp config)
assets/                                                         → build OUTPUT + static production assets (see below)
.github/workflows/deploy.yml                                    → CI build + SFTP deploy to staging (push to dev)
.github/workflows/deploy-production.yml                        → CI build + SFTP deploy to production (push to main)
```

A few root PHP files (`nov-functions.php`, `oct-25-header.php`, `old-functions.php`, `one-signal-header.php`, `sept-functions.php`, `june-footer.php`, `header-stage.php`, `nov-header.php`, `oct-25-functions.php`) are dated snapshots left over from past edits — WordPress doesn't load any of them (only `functions.php`/`header.php`/`footer.php` are active). They're kept in git history for reference but excluded from deploy (see the exclude lists in `.github/workflows/deploy.yml`).

### About `assets/`

`assets/` is tracked in git, not ignored. Only `assets/css/{global,core,tpl-agenda,tpl-events,tpl-flexible,tpl-home,tpl-portal-flexible}.min.css` and `assets/js/main.min.js` are actually regenerated by the build — the rest of it (most images, all webfonts, `admin.css`, MediaElement's control icons) is static production content with no `source/` equivalent, so it has to be committed directly. CI rebuilds the generated files fresh before every deploy regardless of what's committed, but since the built files are still committed (not gitignored), keep them in sync locally too when you touch `source/scss` or `source/js` — run the matching `build:*` task and commit the result alongside your source change, rather than leaving it for CI to silently regenerate.

`assets/css/main.min.css`, `march-24-main.min.css`, and `oct-23-main.min.css` were leftovers from before the CSS bundle split below - dead, unreferenced snapshots of the old combined stylesheet. `march-24-main.min.css`/`oct-23-main.min.css` were already excluded from deploy (see `sync-delta-excludes`/`ftp-mirror-options` below); `main.min.css` has now been added to the same exclude lists. All three have been removed from git. Since the delta-sync deploy's `git diff --diff-filter=ACMRT` doesn't pick up deletions, this removal alone won't clean any stale copies off the live server - a `sync: full` run is needed for that (see "Deployment" below), same caveat that already applied to the other two.

### CSS bundle split

CSS used to compile into one `main.min.css` combining every template's styles, loaded on every page regardless of which template was active. `source/gulp/tasks/build/styles.js` now compiles seven bundles instead, and `adapt_enqueue_template_styles()` in `functions.php` (hooked on `wp_enqueue_scripts` at priority `1`, so it prints before plugin-registered stylesheets) enqueues only the ones a given page needs:

- `global.min.css` — vendor libraries + base/forms/sections/print + header/footer partials. Always loaded.
- `core.min.css` — every `templates/**/*.scss` file except the ones split out below. Default bundle for any template not explicitly special-cased.
- `tpl-agenda.min.css` — `templates/template-agenda.php` only.
- `tpl-events.min.css` — `templates/template-events.php`, loaded alongside `core.min.css` (not instead of it) for `templates/template-events-portal.php`, which shares its wrapper classes but also depends on a shared component partial that lives in `core.min.css`.
- `tpl-flexible.min.css` — `templates/template-flexible.php` only, a verified-safe subset (see `source/scss/main-tpl-flexible.scss`'s header comment for the selector cross-reference this required).
- `tpl-home.min.css` — `templates/template-home.php` only, same verified-safe-subset treatment as flexible (see `source/scss/main-tpl-home.scss`). **Not the live homepage** despite the name — see below.
- `tpl-portal-flexible.min.css` — `templates/template-portal-flexible.php` only, same verified-safe-subset treatment (see `source/scss/main-tpl-portal-flexible.scss`). This is the template actually assigned to the site's static front page (confirmed live via the `template-portal-flexible` body class) — `template-home.php` is an older/unused homepage variant still present in the codebase. Covers all three of its `membershipType` branches (`free-trial`, `advantage`, and the it-pro/professional fallback), since they're all rendered from this one template file.

Splitting a template out requires the same verification each time: grep every other template/component `.php` file for usage of that template's SCSS selectors and confirm there's no cross-reference before excluding it from `core.min.css`. Most of the site's ~50 page templates share styling through reusable ACF flexible-content component partials (`get_template_part()`) in ways that aren't cleanly attributable to one template without tracing selector-by-selector — those all still load the full `core.min.css`, same CSS they've always gotten, no regression. Splitting more of them out is real, valuable follow-up work, but needs the same verification treatment per template before it's safe.

To split another template: add `source/scss/main-tpl-{name}.scss` (import `global/_mixins`, `global/_variables`, and the template's own `templates/_{name}.scss` — check whether it references any `$variables` beyond those two files first), exclude that `templates/_{name}.scss` from `source/scss/main-core.scss`'s import list, add a `compileBundle(...)` call in `styles.js`, and add the matching `is_page_template()` branch in `adapt_enqueue_template_styles()` (`functions.php`). Add the new filename to `sync-delta-includes` / `ftp-mirror-options` in both `deploy.yml` and `deploy-production.yml`.

## Deployment (CI/CD)

Two parallel workflows, one per environment — same build, same deploy mechanism, different branch and different target server:

| Branch | Workflow | Deploys to |
|---|---|---|
| `dev` | `.github/workflows/deploy.yml` | Staging |
| `main` | `.github/workflows/deploy-production.yml` | Production |

Either one also runs manually via the Actions tab → "Run workflow" on the relevant branch. Both do the same thing:

1. Check out the repo with full history (`fetch-depth: 0` — required for delta sync), install Node deps, run `npx gulp _build`
2. Deploy straight from the repo root over SFTP using [`milanmk/actions-file-deployer`](https://github.com/milanmk/actions-file-deployer), with **delta sync**: diffs `git diff <previous commit>..<head>` and only uploads/deletes what actually changed, instead of re-uploading the whole theme every run

Delta sync is git-diff based, which has one important consequence: it can't see changes the build step makes to files that aren't re-committed. The `assets/css/*.min.css` bundles and `assets/js/main.min.js` are committed files, but CI regenerates them fresh in the runner's working directory without committing the rebuild back — so a commit that only touches `source/scss/*.scss` would show those files as "unchanged" in git diff even though the freshly-built content on disk is genuinely different. `sync-delta-includes` in each workflow force-includes all of them in every deploy regardless of git diff, specifically to cover this gap.

Dev-only tracked files (`source/`, `gulpfile.js`, `package*.json`, `.nvmrc`, `README.md`, and the confirmed-dead files listed above) are filtered out via `sync-delta-excludes` (git pathspec syntax) for delta runs, and `ftp-mirror-options` (lftp exclude-glob syntax) for full runs — the same list has to exist in both places (and in both workflow files) since the two sync modes use different underlying mechanisms.

Manually running either workflow via the Actions tab lets you choose `sync: full` instead of the default `delta` — useful for a workflow's first run, or to recover if delta ever drifts from the server's actual state. Full sync mirrors the whole working directory and won't delete anything on the remote that isn't also on the runner.

`main` only gets updated when someone deliberately pushes or merges to it — nothing does that automatically. Pushing to `main` triggers a real production deploy, so treat that push itself as the release step, not routine housekeeping.

### Required GitHub configuration

Two separate GitHub Environments, with **no credentials shared between them** — a compromised staging key should never reach production.

**Settings → Environments → Staging:**

| Name | Type | Value |
|---|---|---|
| `STAGING_USERNAME` | secret | SFTP/SSH username |
| `STAGING_PASS` | secret | **Note:** despite the name, this holds the full SSH private key contents (`-----BEGIN...-----` through `-----END...-----`), not a password. Key auth only. |
| `STAGING_HOST` | variable | Server IP/hostname |
| `STAGING_PORT` | variable | SFTP port (default 22 if unset) |
| `STAGING_REMOTE_PATH` | variable | Absolute path to the theme folder on the server |

**Settings → Environments → Production:**

| Name | Type | Value |
|---|---|---|
| `PRODUCTION_USERNAME` | secret | SFTP/SSH username |
| `PRODUCTION_PASS` | secret | Full SSH private key contents, same format as `STAGING_PASS` — use a different key from staging's |
| `PRODUCTION_HOST` | variable | Server IP/hostname |
| `PRODUCTION_PORT` | variable | SFTP port (default 22 if unset) |
| `PRODUCTION_REMOTE_PATH` | variable | Absolute path to the theme folder on the server |

For both environments: the public half of whatever key is in the `_PASS` secret must already be in `~/.ssh/authorized_keys` for that environment's `_USERNAME` on the corresponding server — GitHub Actions can't add it for you.

If a key is passphrase-protected, add a matching `_SSH_PASSPHRASE` secret and wire it into the `ssh_passphrase` input in that environment's workflow (not currently set for either environment, since no passphrase is configured today).

## Contributing

1. Branch off `dev`
2. `npm install && npx gulp __start` for local dev, or `npx gulp _build` for a one-off build
3. Commit source changes together with the generated `assets/css/*.min.css` / `assets/js/main.min.js` they produce — CI rebuilds these fresh before every deploy regardless, but they're committed files (see "About `assets/`" above), so keep them in sync rather than leaving them stale for whoever reads the repo next
4. Open a PR into `dev` — merging to `dev` triggers an automatic deploy to staging
5. Once verified on staging, push or merge `dev` → `main` to trigger a production deploy
